Key management refers to the secure generation, exchange, storage, and replacement of keys in a cryptographic system. It is a critical aspect of cryptography because even the strongest algorithms are useless if the keys are compromised.
## Types of Keys
### Session Keys
Session keys are temporary secret keys used for a single communication session and then discarded. They are typically used in symmetric-key cryptosystems or for Message Authentication Codes (MAC).

**Benefits:**
*   **Limit Ciphertext Availability:** By changing keys frequently, the amount of ciphertext encrypted with a single key is limited, making cryptanalysis harder for an attacker (Eve).
*   **Limit Exposure:** If a session key is compromised, only the data from that specific session is at risk, not past or future sessions.
*   **Storage Efficiency:** Reduces the need to store a unique long-term key for every possible pair of users. Session keys are generated on-demand.

### Long-term Keys
Long-term keys are intended to be used for an extended period.
*   They are pre-computed and stored securely.
*   **Purpose:** Primarily used to authenticate users and securely exchange session keys.
*   **Types:**
    *   Shared secret keys between two users or between a user and a Trusted Authority (TA) / Key Distribution Center (KDC).
    *   Private keys in a public-key cryptosystem (corresponding to public keys).

## Session Key Distribution

### Key Establishment Schemes
Key establishment involves protocols to agree upon secret keys for secure data exchange. Since symmetric-key cryptography is efficient for encrypting long messages, we often use it for the data itself, but we need a secure way to get the key to both parties.

1.  **Session Key Distribution (with KDC):** A central Key Distribution Center (KDC) or Trusted Authority (TA) selects the session key and distributes it to the users. This is a three-party protocol (Alice, Bob, KDC).
2.  **Key Agreement:** Users negotiate a session key directly over a public channel without a centralized KDC. This typically involves two parties.

### Session Key Distribution with KDC
In this model, the KDC shares a long-term secret key with every user.
*   $K_A$: Long-term secret key shared between Alice and KDC.
*   $K_B$: Long-term secret key shared between Bob and KDC.
*   $K_{AB}$: The session key to be established between Alice and Bob.

![[Pasted image 20251128105144.png]]

**Protocol Flow:**
1.  Alice requests a key for communicating with Bob.
2.  KDC generates $K_{AB}$.
3.  KDC sends $K_{AB}$ to Alice, encrypted with $K_A$. It also includes a copy of $K_{AB}$ encrypted with $K_B$ for Alice to forward to Bob.

**Vulnerabilities:**
*   **Replay Attacks:** If Eve captures the encrypted package intended for Bob ($E_{K_B}(A, B, K_{AB})$), she might be able to replay it later. Bob has no guarantee of "freshness" and might believe he is starting a new session with an old, potentially compromised key.

### Needham-Schroeder Key Distribution
The Needham-Schroeder protocol introduces **nonces** (random numbers used once) to ensure freshness and prevent replay attacks.
*   $N_A$: Nonce generated by Alice.
*   $N_B$: Nonce generated by Bob.

![[Pasted image 20251128105253.png]]

**Protocol Steps:**
1.  $A \to KDC: A, B, N_A$ (Alice identifies herself, Bob, and sends a nonce).
2.  $KDC \to A: E_{K_A}(N_A, B, K_{AB}, E_{K_B}(K_{AB}, A))$
    *   Alice decrypts this. Seeing $N_A$ assures her the message is fresh and from the KDC.
    *   She extracts the ticket $E_{K_B}(K_{AB}, A)$ to send to Bob.
3.  $A \to B: E_{K_B}(K_{AB}, A)$
    *   Bob decrypts the ticket to get the session key $K_{AB}$.
4.  $B \to A: E_{K_{AB}}(N_B)$ (Bob challenges Alice to prove she holds $K_{AB}$).
5.  $A \to B: E_{K_{AB}}(N_B - 1)$ (Alice proves she can decrypt and modify the nonce).

**Known Session Key Attack:**
If Eve manages to obtain an old session key $K_{old}$ and the corresponding ticket, she can replay the ticket to Bob. If Bob doesn't check timestamps (which Needham-Schroeder originally didn't use), he might accept the old key. Eve can then impersonate Alice using $K_{old}$.

### Improvement: Simplified Kerberos V5
To fix the vulnerabilities in Needham-Schroeder (specifically the replay of old keys), Kerberos introduces **timestamps** to define a lifetime $L$ for the key.

![[Pasted image 20251128105917.png]]

**Mechanism:**
1.  The KDC specifies a lifetime $L$ for the session key.
2.  The message includes a timestamp $T$.
3.  Bob verifies that the current time is within $(T, T+L)$. If not, the key is rejected.

**Security Goals:**
*   **Anti-Replay:** Preventing Eve from replaying old messages ($y_1$) containing Alice's challenge.
*   **Active Adversary Prevention:** The lifetime $L$ ensures that even if messages are stored, they cannot be used after they expire.
*   **Mutual Key Confirmation:** 
    *   Bob knows the key came from KDC (encrypted with $K_B$).
    *   Alice knows Bob received the key (by his response).

## Key Agreement without KDC

How can two parties establish a secure key over an insecure channel without a trusted third party? We use public-key concepts, specifically the Diffie-Hellman protocol.

### [[ElGamal-Cryptosystem#Diffie-Hellman Key Exchange|Diffie-Hellman]] Key Agreement (DH)

![[Pasted image 20251128110250.png]]

**Setup:**
*   Public parameters: A large prime $p$ and a generator $g$ (primitive root mod $p$). 

**Protocol:**
1.  **Alice:** Picks a private random number $x$. Computes public value $X = g^x \pmod p$. Sends $X$ to Bob.
2.  **Bob:** Picks a private random number $y$. Computes public value $Y = g^y \pmod p$. Sends $Y$ to Alice.
3.  **Key Computation:**
    *   Alice computes $K = Y^x \pmod p = (g^y)^x = g^{xy} \pmod p$.
    *   Bob computes $K = X^y \pmod p = (g^x)^y = g^{xy} \pmod p$.

**Security:**
*   **Passive Attacks:** Secure based on the **Computational Diffie-Hellman (CDH)** assumption (given $g^x, g^y$, it is hard to compute $g^{xy}$). Ideally, it relies on the **Discrete Logarithm Problem (DLP)** being hard (given $g^x$, hard to find $x$).
*   **Active Attacks:** **Vulnerable.** Standard Diffie-Hellman provides no authentication.

### Man in the Middle Attack (MitM)
Because there is no identity authentication, Eve can intercept the key exchange.

![[Pasted image 20251128110517.png]]

1.  Alice sends $g^x$. Eve intercepts it and sends $g^z$ to Bob.
2.  Bob sends $g^y$. Eve intercepts it and sends $g^z$ to Alice.
3.  Alice computes shared key with Eve: $K_{AE} = (g^z)^x$.
4.  Bob computes shared key with Eve: $K_{BE} = (g^z)^y$.
5.  Eve can decrypt messages from Alice, read/modify them, and re-encrypt them for Bob. Neither Alice nor Bob realizes Eve is listening.

### Station-to-Station (STS) Protocol
To prevent MitM attacks, we add **authentication** (digital signatures) to the Diffie-Hellman exchange.

**Setup:**
*   $p, q$ are large primes where $q | (p-1)$.
*   $\alpha$ is an element of order $q$ in $\mathbb{Z}_p^*$.
*   Users have long-term public/private key pairs for digital signatures.

![[Pasted image 20251128111112.png]]

**Protocol Flow:**
1.  **Alice (U):** Picks random $u$, computes $\alpha^u$. Sends to Bob (V).
2.  **Bob (V):**
    *   Picks random $v$, computes $\alpha^v$.
    *   Computes session key $K = (\alpha^u)^v$.
    *   Generates a signature $Sig_V$ on $(ID_V, \alpha^v, \alpha^u)$.
    *   Sends $\alpha^v$ and the encrypted signature $E_K(Sig_V)$ to Alice.
3.  **Alice (U):**
    *   Computes session key $K = (\alpha^v)^u$.
    *   Decrypts and verifies Bob's signature. This confirms Bob computed the same key and is who he says he is.
    *   Generates signature $Sig_U$ on $(ID_U, \alpha^u, \alpha^v)$.
    *   Sends encrypted signature $E_K(Sig_U)$ to Bob.
4.  **Bob (V):** Decrypts and verifies Alice's signature.

**Why is it Secure?**
*   **Mutual Key Confirmation:** Both parties verify signatures that include the ephemeral public keys ($\alpha^u, \alpha^v$).
*   **Key Freshness:** The session key depends on fresh random values $u$ and $v$.
*   **Forward Secrecy:** Even if long-term signing keys are compromised later, the session key $K$ (derived from random $u, v$) remains secure (assuming DLog is hard).
